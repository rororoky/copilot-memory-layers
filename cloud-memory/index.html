Chapter 04 · How memory behaves

Cloud Copilot Memory

Copilot Memory is the shared, server-side system used by Copilot CLI, the cloud agent, code review, and VS Code. It stores exactly two kinds of memory, and the difference between them is the difference between a team wiki and a personal notebook.

Two types, two audiences

Repository-level facts User-level preferences
What they capture Conventions, architectural decisions, build and test commands, project rules. Your stated preferences, approval habits, and workflows across projects.
Where they apply Only in operations on that repository. Across all your repositories.
Who can see them Anyone with read access to the repository who can use Copilot Memory. You. Administrators can view and export on managed plans.
Who creates them Users with write access to the repository. Only you, from your own interactions.
How they are cited Citations pointing at the code that supports the fact. Citations that may quote what you said.

Source: About GitHub Copilot Memory.

How memories are created

You do not write a memory. Copilot creates them as a byproduct of working with you, and chooses the type based on who the memory applies to — not on who happened to say it.

  • “This repository uses Vitest for unit tests” is true for everyone, so it becomes a repository fact.
  • “Explain your changes before you apply them” is about one person, so it becomes a user preference.
  • If the intent is ambiguous, Copilot is supposed to ask which scope you meant.

You can also ask explicitly — “remember that…” — and on some surfaces Copilot will ask for approval before storing. Cloud agent and code review never ask.

Recall is selective, by design

Memories are not dumped into every prompt. Relevant repository facts and preferences are recalled when a session starts, and only a subset reaches the model. Upvoted memories are more likely to be included.

The consequence

A memory can exist, be correct, and still not influence the response you are looking at. This is why important rules belong in custom instructions rather than in memory.

Where Copilot Memory is used

The same service backs several surfaces, and facts learned in one can inform another.

Surface Repository facts User preferences
Copilot CLIYesYes
Copilot cloud agentYesYes
Copilot code reviewYesNo
Agentic AutofixYesNo
Visual Studio CodeYesYes
Copilot app, mobile, Slack, TeamsYesYes, where available

Availability depends on plan, settings, and organisation policy. Code review and autofix never apply personal preferences, so a preference cannot change how your pull requests are reviewed.

The switches that matter

  1. Your personal setting on GitHub controls whether user-level preferences can be stored and used. It does not control repository facts.
  2. Organisation or enterprise policy can allow or restrict user preferences, and can scope repository access to all, some, or no repositories.
  3. Repository settings can turn off repository facts for one repository without turning off user preferences.
  4. Your client has its own switch — chat.copilot.memory.enabled in VS Code, /memory on|off in the CLI.

All four have to allow a memory type before it is used. Turning off one does not turn off the others, which is exactly why asking “is memory on?” rarely has a single answer.
