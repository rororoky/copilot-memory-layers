Chapter 01 · Foundations

Memory, context, and instructions

Three different mechanisms get called “memory”. Conflating them produces most of the confusion around what an agent “knows”, so this chapter separates them before anything else is built on top.

Three mechanisms, one word

When someone says “the agent remembered that”, they could mean any of the following. They have different owners, different lifetimes, and different failure modes.

Mechanism What it holds Who writes it Lifetime
Context window Everything currently in front of the model: prompt, instructions, retrieved memories, conversation, tool results. The harness, per request One request
Instructions Standing guidance such as conventions, commands, and architecture rules. Humans, through review Until the file changes
Memory Preferences and codebase facts accumulated across conversations. Copilot, with your steering Until it decays or you delete it

The third row is the one with a lifecycle. It is written automatically, recalled selectively, and retired when it stops being useful — which is why it behaves differently from the first two.

Where memory sits in the agent loop

An agent is not a single question and answer. It is a loop: assemble context, reason, act with a tool, validate the result, repeat. Memory is a side channel that feeds the assembly step and is written back afterwards.

Instructions are not memory

The distinction matters because the two solve opposite problems. Instructions are authored: a human decides what must be true and commits it. Memory is accumulated: Copilot decides what is worth keeping and curates it later.

Instructions Memory
Author You and your team Copilot, steered by you
Review Pull request, line by line Review lists in settings; no per-line review
Precision Exact wording, exact scope Paraphrased, cited, and judged
Failure mode Ignored or out of date Stale, wrongly recalled, or never recalled
Best for Rules that matter: security, mandatory steps, conventions Detail that would make instruction files long and unmaintainable
Neither is a guarantee

Guidance loaded into context can still be misunderstood, partially followed, or ignored. Deterministic behaviour requires a hook, a test, or a review gate.

Why scope is the thing to learn

Every memory question collapses into two: who is this true for? and how long should it stay true? The first determines the scope — session, repository, or user. The second determines when the memory is retired. Get those right and the rest is detail.

The next chapter turns that into a map of six layers. After that, the scope matrix lets you test each one against a new chat, a different repository, a different person, and the passage of time.
