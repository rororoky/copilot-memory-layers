Chapter 03 · How memory behaves

Local memory scopes

The Local harness writes memories to files on your machine, in three scopes that are easy to confuse and easy to check. Each one answers a different question about how long a fact should survive.

Three directories, three questions

/memories/                 user memory      ← across all workspaces
/memories/repo/            repository memory ← this workspace only
/memories/session/         session memory    ← this conversation only
Session

Scratch space

In-progress plans, intermediate findings, decisions made mid-task. Disappears when the conversation does.

Repository

Project notes

Build commands, architectural decisions, naming conventions. Persists across conversations in the workspace — and stays on your machine.

User

Personal preferences

How you like to work, independent of project. The first 200 lines load automatically at the start of every session.

Test what survives

Change the situation and watch which knowledge survives. The interesting column is the middle one: local repository memory is durable and private, which no other repository-scoped layer manages.

Scope survival matrix

Five situations × three scopes × three storage layers.

Working with the files

You do not need to edit memory files by hand — ask the agent to remember, update, or forget something and it chooses the scope. Two commands manage the files directly.

Command What it does
Chat: Show Memory Files Lists every memory file across all scopes; select one to read it.
Chat: Clear All Memory Files Removes every memory file in every scope. There is no per-file delete command.
Asking is enough

“Remember that I prefer concise commit message subjects” is a complete instruction. The agent picks the scope, creates or updates the file, and cites it next time it is relevant.

Repository-local storage is experimental

With chat.copilot.memory.local.enabled turned on — it is off by default — Copilot harness sessions can store repository memories in .github/copilot-memories.jsonl instead of the cloud service. It requires a GitHub-hosted repository and does not support user-scoped memories.

Review before you commit

That file sits in the working tree and can be included in commits, including commits made by the agent. Cloud settings and organisation policies do not apply to it. Read the contents before you share it, and never store credentials.

Memory or shared project guidance?

Local memory is deliberately personal. When a repository fact stops being yours alone — when the team depends on it — it should move into source control, where it can be reviewed and maintained.

  1. Verify the fact against the code and configuration.
  2. Move it to the appropriate project document or instruction file.
  3. Review the change through your normal process.
  4. Update or remove the local memory so the two cannot drift apart.
